# hv86

[![build](https://github.com/dpteam/hv86/actions/workflows/build.yml/badge.svg?branch=main)](https://github.com/dpteam/hv86/actions/workflows/build.yml)

Гипервизор «по смыслу как Hyper-V», но виртуальные машины исполняет
[v86](https://github.com/copy/v86) — x86-эмулятор, скомпилированный в WebAssembly.
Управляющая часть, служба Windows, окна, снапшоты и отказоустойчивость — на C# и WebView2.

```
 hv86.exe  ──►  менеджер (Hyper-V-подобное окно, WebView2)
              └► служба Windows  ──►  vmhost на каждую ВМ (v86 в WebView2)
```

## Что уже работает

- **Служба Windows**: установка/удаление/автозапуск, лог, переживает перезапуск.
- **Менеджер**: дерево хоста и ВМ, таблица состояний, панель действий, журнал событий,
  визард создания ВМ, контекстное меню, горячие клавиши (F5/F6/F2/Enter/Del), RU/EN.
- **Настройки ВМ**: имя, память, автозапуск, режим/интервал/глубина чекпоинтов,
  политика рестарта и лимит попыток — всё без правки `vm.json`.
- **Клон, экспорт/импорт `.hv86x`** (zip: описание + диски + медиа) и **диагностика**
  одним архивом (логи + описания ВМ + окружение).
- **Проброс TCP-портов** host → guest: `127.0.0.1:2222 → guest:22`; правила в
  настройках ВМ, применяются на лету, всё видно в журнале.
- **Полный TCP из гостя** в режиме `relay` через собственный WISP-сервер
  (без TAP-драйвера и без Node) — идёт рядом с режимом `nat` с пробросом портов.
- **Headless-движок**: ВМ в Node, живёт в сессии службы и не умирает при логауте;
  консоль — VGA-текст с цветами, ввод текстом и скан-кодами.
- **Общая папка** через virtio-9p (9P2000.L): живой каталог хоста в госте,
  read-only по умолчанию; работает в обоих движках (в web — через синхронные
  запросы к хост-серверу, в headless — напрямую через `node:fs`).
- **Правила исходящего трафика**: без ограничений / только интернет (без LAN и
  localhost) / список целей; проверка по адресам, а не по именам. Работают и для
  релея, и для `nat` — в nat решение по каждому запросу принимает хост, поэтому
  страница больше не может сходить на `127.0.0.1` хоста.
- **Консоль ВМ** отдельным окном: экран v86, клавиатура/мышь, пауза, сброс, вставка
  ISO/образа «на горячую», снапшот, скриншот, скрытие окна (ВМ продолжает работать).
  Масштаб экрана `1×` / `2×` / `Fit`, и «Подключиться» работает и для выключенной ВМ —
  как в Hyper-V: окно откроется, а кнопка Start запустит ВМ в нём же.
- **Снапшоты**: снять на работающей ВМ, откатить (возвращается и состояние, и диск),
  удалить; у каждого — своя копия образа диска.
- **Динамическая отказоустойчивость**: кольцо чекпоинтов по таймеру, heartbeat,
  watchdog; упавший `vmhost` поднимается сам, ВМ восстанавливается из свежего
  чекпоинта, счётчик рестартов и события — в UI.
- **Горячая реплика** (`ft.mode=replica`, web-движок): рядом стоит второй процесс
  с последним чекпоинтом; при падении основной он повышается за секунды и ВМ
  продолжает работу, а не загружается заново.
- **Ввод в гостя**: `hv86 --cli type <vm> "dir" --enter` и `vm.keys` в API; в web-консоли
  `Ctrl+V` вставляет текст из буфера обмена хоста (раскладка US).
- **Диски**: raw-образы (sparse), изменения гостя сохраняются на диск при штатной
  остановке; при падении образ остаётся целым, ВМ откатывается к чекпоинту.
- **Пресеты**: FreeDOS, KolibriOS, Oberon, TinyCore, Linux — скачивание с проверкой SHA-256.

## Быстрый старт

Готовый архив (`hv86-<версия>-win-x64.zip`) распаковывается и запускается одним
файлом — служба для начала не нужна:

```bat
hv86.exe                        :: менеджер; движок он поднимет сам
```

В менеджере: **Новая ВМ…** → пресет `FreeDOS 7.22` → **Создать** → **Подключиться**.
FreeDOS грузится за секунду. Дальше — **Сделать снапшот…**, **Вставить ISO…**, **Перезагрузить**.

В этом режиме движок живёт внутри приложения: окно можно закрыть (приложение
останется в трее), а ВМ останавливаются только при выходе из трея — с обычным
сохранением дисков. Если ВМ должны работать без интерфейса и переживать выход из
системы — поставьте службу:

```bat
hv86.exe --service install      :: установить (права администратора)
hv86.exe --service start
```

Из исходников:

```bat
tools\build.cmd                 :: сборка (+ скачивание WebView2 SDK и v86)
bin\hv86.exe                    :: менеджер
```

Движок можно и вручную, в консоли (отладка, второй экземпляр не нужен):

```bat
dotnet bin\hv86.dll --engine      :: движок в консоли, интерфейс подключится к нему
dotnet bin\hv86.dll               :: менеджер
```

## Управление из консоли

Тот же движок, что и у менеджера, доступен из командной строки — через тот же
named pipe, поэтому состояние всегда одно:

```bat
hv86 --cli status
hv86 --cli list
hv86 --cli create --name dev --preset tinycore --memory 256 --disk 256
hv86 --cli start dev
hv86 --cli snapshot dev before-update
hv86 --cli snapshots dev
hv86 --cli revert dev 0001-before-update
hv86 --cli type dev "dir" --enter
hv86 --cli stop dev
hv86 --cli export dev D:\backup\dev.hv86x
hv86 --cli import D:\backup\dev.hv86x
hv86 --cli diagnostics
```

`<vm>` — id, его префикс или имя. Флаг `--json` печатает машинный вывод для скриптов,
коды возврата: `0` — успех, `1` — ошибка, `2` — неверные аргументы.

## Проверка

```powershell
tools\selftest.ps1              # сборка + unit + selftest + реальная загрузка + itest
tools\selftest.ps1 -SkipItest   # без сценария со службой
```

Что именно проверяется:

| команда | что делает |
|---|---|
| `--unit` | формат state-файла v86, применение блоков диска, JSON, пути |
| `--selftest` | вшитые ресурсы, WebView2 Runtime, каталог данных, каталог пресетов, служба |
| `--smoke <образ>` | настоящая загрузка гостя → `save_state` → перезапуск из state |
| `--itest` | движок + vmhost: создать → загрузить → снапшот → убить vmhost → подъём / повышение реплики → откат → удалить |
| `--htest` | headless: FreeDOS в Node, VGA-текст, 9p-протокол, снапшот |

### CI и артефакты

`.github/workflows/build.yml` (GitHub Actions, `windows-2022`) собирает то же, что
`tools\publish.cmd`, при пуше в `main`, на PR и по тегу `v*`:

- качает WebView2 SDK и v86 скриптами `tools\fetch-*.ps1` (кэш — по хэшу скриптов);
- `npm ci` для headless-движка, сборка Release;
- гоняет `--unit`, `--selftest`, `--htest`;
- публикует `hv86-<версия>-win-x64.zip` (exe + `engine\`) и `checksums.txt` в артефакты,
  а по тегу `v*` — ещё и в GitHub Release.

`--smoke` и `--itest` в CI не запускаются: им нужен WebView2 в сессии пользователя,
а на runner'е сессия 0 — тест был бы красным всегда. Эти два шага остаются локальными,
через `tools\selftest.ps1`.

## Честные ограничения

- v86 — **32-битная** машина без SMP: Linux i386, DOS, Win 9x/2000 — да;
  современные 64-битные гости — нет.
- Скорость — единицы-десятки MIPS: это эмулятор, а не KVM.
- `vmhost` — процесс WebView2, поэтому в этом режиме ВМ живут в сессии пользователя.
  Headless-движок (`engine=headless`, Node) снимает это, но показывает только
  VGA-текст: гость с GUI должен работать на web-движке.
- Снапшот содержит копию диска: место на диске = состояние + образ.
- Общая папка (9p) требует драйвера 9p в госте (Linux); символические ссылки
  и блокировки не поддерживаются. В web-движке каждая файловая операция —
  синхронный запрос к хосту, это не файловая система «на скорость».
- При аварийном падении изменения гостя на диске не сохраняются — ВМ откатывается
  к чекпоинту (сохранение диска делается при штатной остановке).
- Один хост, без живой миграции и реплики на вторую машину (M6).
- Реплика требует web-движка и стоит примерно столько же RAM, сколько основная ВМ:
  это второй v86 с тем же образом в памяти. Локальный оффлайн-старт — чекпоинты.
