# Динамическая отказоустойчивость: как это устроено

Цель: ВМ переживает падение своего процесса, а не «перезагружается с нуля».
Инструмент у нас один — `save_state()` из v86 плюс собственный супервизор.

## Что внутри state-файла

`save_state()` сериализует всё состояние машины: регистры, RAM, устройства
(VGA, IDE, PIC, PIT, RTC, сеть, звук) и **кэш записанных блоков дисков**.
Блок — 256 байт; в state попадают только те, что гость менял после старта.

Практические числа с FreeDOS (32 МБ RAM): state ≈ 6 МБ, снятие ≈ 230 мс.
С ростом RAM и «грязных» блоков размер растёт примерно линейно.

## Два разных механизма, не путать

| | снапшот (`snapshots/`) | чекпоинт кольца (`checkpoints/`) |
|---|---|---|
| когда | по команде пользователя | по таймеру `ft.interval_ms` (15 с по умолчанию) |
| состав | `state.bin` + **копия диска** | только `state.bin` |
| зачем | откат к произвольной точке | подъём после падения |
| хранение | все, пока не удалят | последние `ft.keep` (3) |
| откат диска | да, диск перезаписывается копией | нет, диск не трогаем |

Почему так: откат к старому снапшоту должен вернуть и диск, иначе гость увидит
файловую систему из будущего. А кольцу достаточно вернуть RAM+VGA+устройства:
образ диска на хосте в момент падения ещё не изменён (см. ниже), поэтому
восстановление согласовано.

## Согласованность диска

- Штатная остановка: `vmhost` замораживает эмулятор, снимает state, применяет
  «грязные» блоки из state к образу (`src/Vm/V86State.cs`), затем уничтожает
  эмулятор. Диск сохранён.
- Падение: блоки применить некому, образ остаётся как был; ВМ поднимается из
  чекпоинта, где эти блоки уже есть. Потерь и рассогласования нет — теряется
  только то, что гость успел записать *после* последнего чекпоинта.
- Поэтому кольцо очищается при штатной остановке: после записи блоков в образ
  старые чекпоинты уже не соответствуют диску. `NewestRing()` дополнительно
  сверяет «отпечаток» образа (размер + mtime), чтобы не подсунуть чужой диск.

## Watchdog

- `vmhost` шлёт `vm.metrics` раз в секунду; служба запоминает `LastBeatUtc`.
- `Tick()` каждые 2 с: процесс умер → `HandleCrash`; тишина > 10 с → kill и
  `HandleCrash`.
- `HandleCrash`:
  1. `state = recovering`, событие `ft.event{kind=crash}`;
  2. проверка политики (`restart`, `max_attempts`);
  3. `restarts++`, поиск свежего чекпоинта (`NewestRing`);
  4. `start` с `--restore <state>`;
  5. при неудаче — `state = failed` и событие `gave-up`.
- Запуск/восстановление не считается падением: `starting`/`recovering` игнорируются
  первые 120 с (WebView2 + wasm + образ — не мгновенно).

## Бюджет паузы (что ещё не сделано)

Сейчас состояние снимается без адаптивного бюджета: интервал фиксированный.
План M3+:
- измерять длительность `saveState` и держать паузу ≤ 250 мс и ≤ 3 % wall-time;
- увеличивать интервал, когда гость простаивает (по счётчику инструкций);
- уменьшать при активной записи на диск (счётчики `ide-write-end`);
- при нехватке RAM/CPU деградировать ступенями: реже чекпоинты → ниже fps кадров →
  пауза ВМ с низким приоритетом. В UI это должно быть видно как «FT: High/Med/Low».

## Что дальше (M6)

- Горячая реплика: второй `vmhost` получает те же чекпоинты и стоит на паузе;
  переключение = `run()` на реплике (RTO ~1 с).
- Реплика на второй машине: передача state по сети + согласование диска
  (нужен журнал записей, чтобы реплика не разъехалась с первичным хостом).
- Живая миграция — отдельный разговор: у v86 нет dirty-page tracking, придётся
  его эмулировать на уровне образа диска и состояния.
