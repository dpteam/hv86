# Динамическая отказоустойчивость: как это устроено

Цель: ВМ переживает падение своего процесса, а не «перезагружается с нуля».
Инструмент у нас один — `save_state()` из v86 плюс собственный супервизор.

## Что внутри state-файла

`save_state()` сериализует всё состояние машины: регистры, RAM, устройства
(VGA, IDE, PIC, PIT, RTC, сеть, звук) и **кэш записанных блоков дисков**.
Блок — 256 байт; в state попадают только те, что гость менял после старта.

Практические числа с FreeDOS (32 МБ RAM): state ≈ 6 МБ, снятие ≈ 230 мс.
С ростом RAM и «грязных» блоков размер растёт примерно линейно.

## Три механизма, не путать

| | снапшот (`snapshots/`) | чекпоинт кольца (`checkpoints/`) | реплика (`--replica`) |
|---|---|---|---|
| когда | по команде пользователя | по таймеру `ft.interval_ms` (15 с по умолчанию) | постоянно в `ft.mode=replica` |
| состав | `state.bin` + **копия диска** | только `state.bin` | живой процесс + последний `state.bin` |
| зачем | откат к произвольной точке | подъём после падения | пережить падение без загрузки |
| хранение | все, пока не удалят | последние `ft.keep` (3) | процесс-двойник |
| откат диска | да, диск перезаписывается копией | нет, диск не трогаем | нет, диск как в чекпоинте |

Почему так: откат к старому снапшоту должен вернуть и диск, иначе гость увидит
файловую систему из будущего. А кольцу достаточно вернуть RAM+VGA+устройства:
образ диска на хосте в момент падения ещё не изменён (см. ниже), поэтому
восстановление согласовано.

## Согласованность диска

- Штатная остановка: `vmhost` замораживает эмулятор, снимает state, применяет
  «грязные» блоки из state к образу (`src/Vm/V86State.cs`), затем уничтожает
  эмулятор. Диск сохранён.
- Падение: блоки применить некому, образ остаётся как был; ВМ поднимается из
  чекпоинта, где эти блоки уже есть. Потерь и рассогласования нет — теряется
  только то, что гость успел записать *после* последнего чекпоинта.
- Поэтому кольцо очищается при штатной остановке: после записи блоков в образ
  старые чекпоинты уже не соответствуют диску. `NewestRing()` дополнительно
  сверяет «отпечаток» образа (размер + mtime), чтобы не подсунуть чужой диск.

## Watchdog

- `vmhost` шлёт `vm.metrics` раз в секунду; служба запоминает `LastBeatUtc`.
- `Tick()` каждые 2 с: процесс умер → `HandleCrash`; тишина > 10 с → kill и
  `HandleCrash`.
- `HandleCrash`:
  1. есть прогретая реплика → `vm.promote` и выход (ВМ продолжает работу);
  2. иначе `state = recovering`, событие `ft.event{kind=crash}`;
  3. проверка политики (`restart`, `max_attempts`);
  4. `restarts++`, поиск свежего чекпоинта (`NewestRing`);
  5. `start` с `--restore <state>`;
  6. при неудаче — `state = failed` и событие `gave-up`.
- Запуск/восстановление не считается падением: `starting`/`recovering` игнорируются
  первые 120 с (WebView2 + wasm + образ — не мгновенно).

## Бюджет паузы (что ещё не сделано)

Сейчас состояние снимается без адаптивного бюджета: интервал фиксированный.
План M3+:
- измерять длительность `saveState` и держать паузу ≤ 250 мс и ≤ 3 % wall-time;
- увеличивать интервал, когда гость простаивает (по счётчику инструкций);
- уменьшать при активной записи на диск (счётчики `ide-write-end`);
- при нехватке RAM/CPU деградировать ступенями: реже чекпоинты → ниже fps кадров →
  пауза ВМ с низким приоритетом. В UI это должно быть видно как «FT: High/Med/Low».

## Горячая реплика (`ft.mode = replica`)

Второй процесс той же ВМ: `hv86 --vmhost <id> --replica`, свой канал
`\\.\pipe\hv86-vm-<id>-r` (обычный канал занят основной), своя папка профиля
WebView2 (`webview\vm-<id>-replica`) — два процесса не могут делить один
user data folder.

Жизненный цикл:

1. Основная ВМ запущена → служба поднимает реплику **без** `--restore`: страница
   стартует в режиме `paused` (CPU не запускается, экран не рисуется).
2. Реплика получает последний чекпоинт кольца (`vm.restoreState <path>`):
   страница делает `stop()` → `fetch(state)` → `restore_state(buffer)` и
   отвечает `restoreDone` — служба ждёт именно этот ответ, а не состояние
   «paused» (его страница выставляет ещё до восстановления). После этого
   реплика `warm`.
3. Каждый новый чекпоинт служба сразу отдаёт реплике, поэтому её отставание —
   один интервал `ft.interval_ms`, а не всё время с момента старта.
4. Падение основной: `HandleCrash` → `vm.promote` → страница делает `run()`.
   Служба переключает `runtime.Proc` на реплику (канал остаётся `-r`),
   `restarts++`, событие `ft.event{kind=promoted}`, и поднимает новую реплику.
5. Если реплику убить или она отвалится, сторож (`SuperviseReplica`) поднимает
   новую через 15 с; основная ВМ при этом не трогается.

Сеть: реплика не занимает портов и не поднимает релей, но **знает** порт релея
основной (`--relay-port`). Адрес `wisp://127.0.0.1:<порт>` попадает в state,
поэтому после повышения реплика поднимает релей на том же порту и правила
проброса снова применяются к живому гостю. Иначе гость после переключения
остался бы без сети: его состояние помнит адрес, которого больше нет.

Чего реплика не даёт: потери за последний интервал всё равно есть (state
отстаёт), а диск выравнивается по последнему чекпоинту — блоки, записанные
гостем после него, в реплику не попадают.

Реплика есть только у web-движка: в headless второй экземпляр не нужен, там
остаются чекпоинты (и это пишется в лог).

## Что дальше (M6)

- Реплика на второй машине: передача state по сети + согласование диска
  (нужен журнал записей, чтобы реплика не разъехалась с первичным хостом).
- Живая миграция — отдельный разговор: у v86 нет dirty-page tracking, придётся
  его эмулировать на уровне образа диска и состояния.
