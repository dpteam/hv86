# WISP в hv86: зачем и как

Документ про `src/VmHost/WispRelay.cs` — свой сервер протокола WISP, который
даёт гостю произвольный TCP наружу.

## Проблема

`fetch`-backend v86 (режим `nat`) проксирует наружу **только HTTP(S)**: он
разбирает запросы гостя и повторяет их через `fetch()` страницы. Ни `apt`,
ни `git`, ни `ssh` так не работают. Варианты, которые отпадают:

| вариант | почему нет |
|---|---|
| `wsproxy` + TAP | нужен TAP-драйвер, права администратора, dnsmasq рядом |
| свой ethernet/TCP-стек в C# | это недели работы и постоянный источник багов |
| WISP-сервер на Node (`wisp-js`) | тащит Node в поставку (он появится только в M5) |
| публичный WISP-сервер | чужой трафик через чужую машину, задержки, приватность |

Остаётся свой сервер WISP на C#: протокол маленький (4 типа пакетов),
соединение наружу открывает наш процесс, гостю сеть не нужна.

## Протокол (v1.2, кратко)

Транспорт — WebSocket, бинарные сообщения; одно сообщение = один пакет:

```
uint8 type | uint32 stream_id (LE) | payload
```

| type | имя | payload |
|---|---|---|
| 0x01 | CONNECT | `uint8 stream_type` (1=TCP, 2=UDP), `uint16 port`, hostname (UTF-8) |
| 0x02 | DATA | байты в сокет / из сокета |
| 0x03 | CONTINUE | `uint32` свободных пакетов в буфере сервера |
| 0x04 | CLOSE | `uint8 reason` |

Сразу после handshake сервер обязан отправить `CONTINUE` для `stream_id = 0`
(это версия протокола) — клиент ждёт его перед первой отправкой.

Коды закрытия, которые мы отдаём: `0x41` невалидный запрос, `0x42` хост не
резолвится, `0x43` таймаут, `0x44` connection refused, `0x47` ошибка передачи,
`0x49` слишком много потоков.

## Что именно сделано

- **WebSocket-сервер вручную** (`TcpListener` + хендшейк + кадры), а не
  `HttpListener`: тот работает через http.sys и требует URL ACL. vmhost живёт
  под обычным пользователем, где ACL нет и не будет.
- Порт: `TcpListener` на `127.0.0.1:0`, то есть свободный порт от ОС.
  Адрес передаётся странице как `relay_url: "wisp://127.0.0.1:<port>"`.
- Ограничения: 128 потоков на соединение, буфер 4 МБ на поток до установки
  соединения, таймаут установки 12 с, максимальный websocket-кадр 1 МБ.
- TCP: `TcpClient.ConnectAsync`, чтение 32 КБ, отправка в `DATA`; закрытие
  сокета → `CLOSE(0x02)`.
- UDP: реализован на сервере (`UdpClient`), но клиент v86 UDP пока не шлёт —
  v86-стек делает DNS через DoH, а не через UDP.

## Почему страница консоли на `http://`, а не `https://`

Релей слушает `ws://127.0.0.1:<port>`. Chromium блокирует небезопасный `ws://`
из документа, открытого по https (mixed content). Поэтому `VmResourceServer`
отдаёт страницу по `http://hv86.local`; других причин для https у локальной
страницы из вшитых ресурсов нет.

Проверено автотестом `--itest`: после перезапуска ВМ в режиме `relay` счётчик
`relay_clients` становится ≥ 1 — то есть **сама страница v86** успешно
подключилась к релею, а не только наш тестовый клиент.

## Как проверяется

`--itest` поднимает локальный echo-сервер, переключает ВМ в `relay`, ждёт порт
релея и подключение v86, затем `WispTestClient` проходит полный цикл:
handshake → CONTINUE(0) → CONNECT(echo:port) → DATA("hv86-relay") → DATA обратно.

## Что дальше

- Правила исходящего трафика (что гостю можно, что нет) — сейчас релей пускает
  куда угодно, включая локальную сеть хоста.
- UDP со стороны v86 (пока протокол поддерживает только TCP).
- Возможная замена режимов на «nat + relay одновременно»: сначала пробуем
  `fetch` для проброса, а TCP-исходящие шлём в релей. Для этого нужен
  собственный транспорт внутри гостя (агент), иначе NIC один.
