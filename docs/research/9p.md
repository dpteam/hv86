# Общая папка: 9p (9P2000.L)

Документ про `engine/fs9p.mjs` — сервер протокола 9p, через который гость
видит настоящую папку хоста.

## Почему 9p и как это устроено

v86 умеет отдавать гостю virtio-9p и принимает три варианта бэкенда:
`basefs/baseurl` (снимок папки, сделанный `copy-to-sha256.py` — не живая папка),
`proxy_url` (внешний 9p-сервер по WebSocket) и `handle9p` (функция в JS,
получающая сырые кадры). Нам нужна живая папка, поэтому — `handle9p`.

`handle9p` **синхронный**: пришёл кадр — сразу вернули ответ. Поэтому протокол
(разбор кадров, fid'ы, qid) вынесен в `engine/fs9p.mjs` и не знает, где лежат
файлы: он работает с **относительными** путями и адаптером `fs`.

| движок | адаптер | как читает/пишет |
|---|---|---|
| headless (Node) | `engine/fs-node.mjs` | `node:fs` (синхронно) |
| web (WebView2) | `engine/fs-xhr.mjs` | синхронный POST к `/share`, выполняет `VmHost/ShareFileServer.cs` |

В браузере нет ни `fs`, ни `node:path`, поэтому в JS не остаётся ни одного
хост-пути: страница присылает «a/b/c.txt», а настоящий путь, проверки и
симлинки — на стороне C#. Это же снимает вопрос «а доверяем ли мы странице»:
не доверяем, она просит операцию, а решает сервер.

Почему не `proxy_url` (9p по WebSocket): пришлось бы писать второй сервер
протокола на C#. С синхронным XHR протокол остаётся один на оба движка.

Синхронный XHR в WebView2 проверен автотестом `--itest`: страница делает
`POST /share {op:"stat"}`, сервер отвечает настоящим `size`, и там же
проверяется, что модули `fs9p.mjs`/`fs-xhr.mjs` загрузились в страницу.

## Диалект

При `handle9p` устройство ничего не разбирает само: любой кадр уходит в нашу
функцию. Ядро Linux по умолчанию просит **9P2000.L**, поэтому реализован `.L`,
а не классический 9P2000 (там другой формат stat и другие коды сообщений).

Монтирование в госте:

```sh
mkdir -p /mnt/share
mount -t 9p -o trans=virtio,version=9p2000.L host9p /mnt/share
```

Тег `host9p` — как в документации v86.

## Что реализовано

| операция | поведение |
|---|---|
| Tversion / Tattach | msize ≤ 8192, корень шары |
| Twalk / Tlopen / Tread / Twrite / Tclunk | обычные файлы, offset-based ввод-вывод |
| Tgetattr / Tsetattr | stat (153 байта по спеке), truncate и chmod |
| Treaddir | записи `qid + offset + type + name`, смещения — байтовые |
| Tlcreate / Tmkdir / Tunlinkat / Trenameat | создание, удаление, переименование |
| Tfsync / Tstatfs | fsync по открытому fd, свободное место |
| Tlocks / Tsymlink / Tlink / Tmknod | `EOPNOTSUPP` (Windows-шарa, смысла нет) |
| Tauth | `EOPNOTSUPP` (аутентификация не нужна) |

Ошибки отдаются как `Rlerror` с POSIX errno (ENOENT, EACCES, EROFS, …).

## Безопасность

- Все пути разрешаются относительно корня шары; `..`, `/`, `\` и NUL в компонентах
  отвергаются. `..` в `walk` поднимает наверх, но не выше корня.
- Симлинки разыменовываются и проверяются по `realpath` **с настоящим корнем**
  (на Windows короткие имена вроде `DARTPO~1` иначе ломают сравнение) — ссылка
  наружу даёт `EACCES`.
- Режим «только чтение» (`readonly`) отбивает Twrite/Tlcreate/Tmkdir/… с `EROFS`.
- Всё, что отдаётся гостю, — только содержимое выбранной папки. Никакого
  доступа к остальному диску.
- В web-движке те же проверки делает `ShareFileServer` (C#): страница присылает
  относительный путь, настоящий путь и решение «можно ли» — только на сервере.

## Как проверяется

`node engine/test-9p.mjs` — клиент протокола, без гостя: version, attach,
walk, open/read/write, getattr (проверка, что это обычный файл), readdir,
mkdir/rename/unlink, `..` (подъём и обрезка на корне), отказ на компонент
с разделителем, отказ на симлинк наружу, `EROFS` в read-only режиме.

Этот тест запускается из `hv86 --htest` (шаг «9p protocol»), а `--htest` входит
в `tools\selftest.ps1`.

Для web-движка `--itest` проверяет транспорт и хост-часть: синхронный
`POST /share` со страницы возвращает настоящий `stat`, и модули 9p грузятся
в страницу.

`--unit` покрывает `ShareFileServer` (C#): stat/readdir/read/write-at-offset,
mkdir/rename, отказ на `..`, на `\`, на абсолютный путь, `EROFS`.

## Чего нет и почему

- Симлинки/жёсткие ссылки/mknod — на Windows их либо нет, либо они не имеют
  смысла в шаре; гостю возвращается `EOPNOTSUPP`.
- Блокировки (Tlock/Tgetlock) — не поддерживаем, для «перекинуть файлы» не нужны.
- Права/владельцы — отдаём uid/gid 0 и права по маске, Windows ACL в POSIX
  всё равно не отображается один-в-один.
- Web-движок: там `handle9p` синхронный, а ввода-вывода с хоста в странице нет —
  сделан синхронный XHR к `/share` (см. выше). Ограничение — скорость: каждый
  запрос это HTTP-обмен внутри процесса, для «перекинуть файлы» достаточно,
  для баз данных в шаре — нет.

## Проверка с настоящим гостем (не автоматизирована)

В репозитории нет Linux-образа с модулем `9pnet_virtio`, поэтому монтирование
в живом госте не проверялось. Что проверено: протокол (своим клиентом) и то,
что ВМ с шарой стартует и работает. Если `mount` в госте не проходит —
первым делом смотреть лог движка: сервер пишет причину каждого отказа.
