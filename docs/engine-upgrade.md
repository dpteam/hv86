# Движок v86: версия, обновление, совместимость

v86 живёт в exe как ассеты (`assets/v86/<version>/`), а не как внешняя зависимость:
один файл, офлайн, никаких «скачается при первом запуске». За это платим
пиннингом: **state v86 между версиями несовместим**, и обновление движка —
операция над ВМ, а не замена файла.

## Где живёт версия

| место | что там | кто пишет |
|---|---|---|
| `src/Core/AppInfo.cs` | `V86Version` — что вшито в exe | человек, при обновлении |
| `assets/v86/manifest.json` | версия, размеры, SHA-256 каждого файла | `tools/fetch-v86.ps1` |
| `vms/<id>/vm.json` | `v86_version` — на чём ВМ создана | при создании ВМ |
| `snapshots/<id>/meta.json` | `v86_version` снапшота | при снапшоте |
| `checkpoints/ring-*.json` | `v86_version` чекпоинта | при чекпоинте |

## Что происходит, если версии разошлись

- **Запуск ВМ** — отказ с текстом, в котором есть готовая команда:
  `ВМ сделана на v86 X, а встроен Y … hv86 --cli migrate <vm>`.
  Раньше здесь было предупреждение в лог и запуск «как есть»: гость поднимался,
  а падал позже и по непонятной причине.
- **Снапшот/чекпоинт чужой версии** — не откатывается (`CheckpointStore`
  сверяет `v86_version` с версией ВМ).
- **vmhost, запущенный руками** — выходит с кодом 4, а не пытается работать.
- **`--selftest`** сверяет вшитые файлы с манифестом (размер + SHA-256) и печатает
  версию из манифеста рядом с версией приложения. Это ловит сборку, где файл
  заменили, а версию/хэши забыли: иначе ВМ считалась бы созданной на одной
  версии, а исполнялась другой.

## Перенос ВМ (`vm.migrate`)

```
hv86 --cli migrate <vm>          # ВМ должна быть остановлена, окно закрыто
```

Диски, медиа, настройки — остаются. Снапшоты и кольцевые чекпоинты старой версии
уходят в корзину: они физически несовместимы, и «сохранить на всякий случай»
означало бы однажды откатить ВМ в нерабочее состояние. Отчёт о переносе
(`snapshots`, `checkpoints`) возвращается в UI и CLI, чтобы потеря не была немой.

Открытое окно ВМ мешает переносу намеренно: у окна своя копия `vm.json`, и она
вернула бы старую версию обратно.

## Как обновить движок (чек-лист)

1. `powershell -File tools\fetch-v86.ps1 -Version <новая>` — скачает npm-пакет
   (`build/libv86.js`, `build/v86.wasm`) и BIOS из репозитория copy/v86,
   посчитает SHA-256 и перезапишет манифест.
2. `powershell -File tools\fetch-v86.ps1 -Check` — сверка файлов с манифестом.
3. В `hv86.csproj` — пути `assets\v86\<новая>\…`, в `AppInfo.cs` — `V86Version`.
   LogicalName ресурсов не меняются (`Hv86.Assets.v86.*`): версия одна на сборку.
4. `dotnet build` → `--unit` → `--selftest` → `--smoke <образ>` → `tools\selftest.ps1`.
5. Boot-матрица по каталогу: `tools\old-dos-smoke.mjs` на отобранных кандидатах
   и `tools\old-dos-boot.ps1` на готовых пресетах. Расхождения — в этот файл.
6. Проверить `vm.migrate` на ВМ, созданной предыдущей сборкой (снапшоты должны
   уйти, диски остаться), и убедиться, что старая ВМ без переноса не стартует.

Ассеты одной версии вшиваются в exe (сейчас ~2.4 МБ). Держать две версии сразу
смысла нет: перенос дешевле, чем двойной размер и две ветки поведения.

## Состояние на 2026-11-07

- Вшита **v86 0.5.473** (npm, опубликована 2026-10-30) — это последняя
  опубликованная версия; `dist-tags` npm содержит только `latest: 0.5.473`.
- Сборка с `copy.sh/v86/build` (master, 2026-07-05) **старше** нашей и отличается
  сборкой wasm (1.4 МБ против 2.0 МБ) — как источник обновления не годится.
- `seabios.bin` и `vgabios.bin` из master репозитория copy/v86 совпадают с нашими
  байт-в-байт: BIOS обновлять нечего.
- Совместимость подтверждена загрузкой (не «должно работать»): FreeDOS, ELKS,
  KolibriOS, MS-DOS 5.0/6.0/6.2x, PC DOS 2.0–7.0, DR-DOS/Novell DOS,
  Concurrent DOS, PC-MOS, Debian 0.93, PTS-DOS, Windows NT 3.51 (setup),
  Windows 1.x–3.x (setup-диски грузятся, но система ставится только поверх DOS).
  Не грузятся: незагрузочные CD (нет El Torito) и диски данных — см.
  `docs/research/old-dos.md`.
