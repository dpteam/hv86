# Реплика на вторую машину (`ft.mode = remote`)

Цель: ВМ переживает падение **хоста**, а не только процесса. Инструмент тот же —
`save_state()` v86 — но состояние уезжает по сети на второй компьютер, который
держит готовую копию диска и последний state.

Документ описывает протокол **до** реализации: это публичный контракт между
двумя экземплярами hv86, и менять его молча нельзя.

## Чего это не даёт (честно)

- **Не живая миграция.** Между основным хостом и репликой расхождение в один
  интервал `ft.interval_ms` (по умолчанию 15 с). Столько работы гостя теряется
  при переключении: RPO = интервал чекпоинта.
- **Не автоматическое переключение без свидетеля.** Два хоста не могут сами
  договориться, кто главный: если сеть разорвалась, оба считают друг друга
  мёртвыми. Без третьей стороны (свидетель) автоматический промоушен — это
  split-brain. Поэтому promotion здесь **ручной**: `hv86 --cli promote <vm>`
  на реплике. Автоматика — отдельный шаг со свидетелем.
- **Не общее хранилище.** Диск копируется на реплику целиком при старте ВМ
  (epoch), дальше летает только state.
- **Не для WAN.** HTTP без TLS, авторизация — общий токен. Считать сеть
  доверенной (LAN, VPN). TLS — когда появится смысл в сертификатах.

## Почему хватает state без журнала записей

v86 держит изменения диска в кэше блоков внутри эмулятора: файл образа на
основном хосте **не меняется** во время работы, он обновляется только при
штатной остановке (см. `docs/research/ft-design.md`). Значит:

```
диск на момент старта ВМ (epoch) + state.bin  =  согласованный срез
```

`state.bin` кумулятивен: в нём все «грязные» блоки с момента старта, а не
дельты между чекпоинтами. Поэтому реплике достаточно базового образа и
последнего state — журнал записей не нужен, пока ВМ не перезапускали.

Как только ВМ штатно остановили и запустили снова, диск изменился → нужен новый
epoch и новый базовый образ. Это же правило защищает от смешивания: реплика
принимает состояние только того epoch, чей образ у неё лежит.

## Раскладка на реплике

```
%ProgramData%\hv86\replica\<vm-id>\
  replica.json     { vm_id, name, epoch, disk_size, disk_sha256,
                     seq, state_size, state_sha256, vm_json, updated_utc }
  disk.img         базовый образ эпохи epoch
  state-<seq>.bin  последний принятый state
```

`replica.json` пишется атомарно (temp → `File.Replace`), как и всё остальное.
Файлов два, а не один: state перезаписывается каждые 15 с, и реплика не должна
остаться без валидного состояния, если запись прервалась.

## Протокол (`/replica/v1/...`, HTTP)

Авторизация: заголовок `X-Hv86-Token: <токен>`, сравнение без утечки времени.
Любой запрос без токена → `401`. Токен задаётся на обеих сторонах
(`ft.replica_token` в `vm.json` основного, `--replica-token` на реплике).

| метод | запрос | ответ | смысл |
|---|---|---|---|
| `GET /hello` | — | `{product, version, max_mb}` | проверка связи и версии |
| `POST /begin` | query: `vm, epoch, name, disk_size`; тело — образ диска | `{ok, epoch}` | новая эпоха: реплика принимает базовый образ (целиком) |
| `PUT /state` | query: `vm, epoch, seq, size, relay_port`; тело — state | `{ok, seq}` | новый state; `seq` должен расти |
| `GET /status` | query: `vm` | `{vm_id, epoch, seq, size, age_sec, warm}` | что лежит у реплики |
| `DELETE /replica` | query: `vm` | `{ok}` | снять реплику с учёта |

Правила, на которых держится корректность:

1. **Version lock.** `hello` отдаёт версию v86; если она не совпадает с версией
   основного хоста — реплика не принимает state (иначе state несовместим, и
   подъём даст мусор). Отказ `409` с текстом.
2. **Epoch.** `begin` с новым epoch заменяет образ и обнуляет seq. `state` с
   чужим epoch → `409` (основной хост перезапустил ВМ, старые блоки не подходят).
3. **Seq.** `state` с `seq <= последнего` → `200 {ok:false, duplicate:true}`:
   повтор после обрыва не ломает реплику (идемпотентность по seq).
4. **relay_port.** Порт релея основного хоста едет вместе со state: адрес
   `wisp://127.0.0.1:<порт>` уже записан в state, и при подъёме реплика обязана
   занять **тот же** порт, иначе гость останется без сети. Необязателен: без него
   реплика поднимется с новым портом, и это будет видно в логе.
4. **Атомарность.** Образ пишется в `disk.img.part` и подменяется `File.Replace`
   только после `begin` с полным телом и совпавшим `disk_sha256`. Недописанный
   образ не становится «базовым».
5. **Только диск и state.** Никаких команд `start/stop` по HTTP: реплика — это
   хранилище, а не удалённое управление. Промоушен — локальная команда службы
   на самой реплике.

## Поток

1. ВМ стартует на основном хосте. Перед первым чекпоинтом он отправляет
   `begin` с базовым образом (то, что лежит в `disks/` на момент старта) и
   `vm_json` для будущего подъёма.
2. Каждый чекпоинт кольца → `PUT /state` с новым `seq`.
3. Основной хост показывает в статусе ВМ `ft: remote, отставание N с` —
   по timestamp последнего успешного `state` и своему `ft.interval_ms`.
4. Падение основного: на реплике `hv86 --cli promote <id>` (или кнопка «Поднять»
   в менеджере, если на хосте есть принятые реплики). Служба реплики:
   - собирает ВМ из `vm_json` (id остаётся тем же, диском становится `disk.img`,
     медиа и флаппи не переносятся — их у реплики нет);
   - переписывает `vm.json` на пути этого хоста и проверяет версию v86 —
     state от другой версии поднимать нельзя;
   - переносит образ и последний state в каталог ВМ (`AtomicFile.Move`, то есть
     переименование, а не копия), принятую копию уводит в корзину;
   - запускает ВМ с `--restore <state>` и портом релея из метаданных;
   - при неудаче ВМ остаётся остановленной **с диском и state на месте** —
     повторный запуск возможен обычным способом, данные не теряются.
   Основной хост при этом должен быть остановлен вручную: fencing'а нет.
5. Обрыв сети: push падает, повтор — по следующему чекпоинту. Отставание
   видно в статусе, реплика остаётся на последнем валидном state.

## Ограничения, которые надо показать в UI

- «Реплика отстаёт на N с» — не молчать.
- «Promotion ручной» — кнопка `promote` в статусе, а не тихий автопереход.
- При `promote` основной хост, если он жив, должен быть остановлен вручную:
  fencing'а нет, и это написано прямо, а не замаскировано.

## Что уже сделано

- Передача образа эпохи и состояния (эта дока) — `ft.mode = remote`.
- Промоушен на реплике: `hv86 --cli promote <id>` и кнопка «Поднять» в списке
  машин, если хост принял реплики. Проверено в `--itest`: снимок работающей ВМ
  уезжает на реплику, поднимается как отдельная ВМ, гость продолжает исполнение
  с этого состояния (213 тыс. инструкций после восстановления).

## Что остаётся на потом

- Свидетель (третья сторона) и lease-токен → автоматический promotion и
  настоящий fencing (остановка «старого» основного).
- TLS + клиентские сертификаты.
- Инкрементальная передача диска (dirty-block journal) — нужна для больших
  образов и для перезапусков без полной копии.
- Перенос медиа (CD/дискеты): сейчас реплика возит только жёсткий диск, поэтому
  ВМ с обязательным CD после подъёма придётся доукомплектовать.
