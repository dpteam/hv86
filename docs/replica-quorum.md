# Свидетель и lease: автоматический подъём без split-brain

Второй хост умеет держать копию состояния и поднимать из неё ВМ
(`docs/replica-remote.md`). Оставался вопрос «кто главный»: два хоста без третьей
стороны не могут договориться, и автоматическое переключение превращается в
split-brain — оба работают, оба пишут.

Решение — **свидетель (witness)**: маленькая служба, которая выдаёт **lease**
(аренду) одному владельцу на время. Кто держит lease — тот и работает.

## Роли

```
        lease          ┌────────────┐
  P ───────────────►   │  witness   │   ── арбитр: только он решает, кто владелец
  │                    └────────────┘
  │ state + lease          ▲
  ▼                        │ claim (если аренда истекла)
  R ───────────────────────┘
```

- **P (основной)**: запускает ВМ, шлёт state на R, продлевает lease у W.
- **R (реплика)**: хранит образ и state; может подняться, только получив lease.
- **W (свидетель)**: хранит `{vm → {holder, token, expires}}`. Больше ничего.

W — отдельный процесс (`hv86 --witness <порт> <токен>`) и должен стоять **не на
тех же двух машинах**: если он живёт на реплике, то падение реплики уносит и
арбитра, и автоматика превращается в «оба стоят».

## Контракт аренды

| параметр | значение | почему |
|---|---|---|
| TTL | 12 с | окно, в котором допускается два «главных» при самом плохом раскладе |
| продление | каждые 4 с | три попытки до истечения |
| проверка репликой | каждую секунду | подъём за ~1 с после истечения |

Правила:

1. **Время считает только W.** Клиенты присылают «продли», W ставит
   `expires = now + ttl` по своим часам. Часы P и R не участвуют в решении —
   иначе рассинхронизация времени ломала бы безопасность.
2. **Аренда выдаётся, только если истекла.** `claim` при живой аренде отвечает
   отказом с остатком времени. Никакого «отбери силой».
3. **Токен меняется при каждой выдаче.** Старый токен после передачи аренды
   недействителен навсегда — это и есть fencing для данных.
4. **P работает, только пока аренда жива.** Не смог продлить до истечения —
   **останавливает ВМ** и пишет событие `fenced`. Лучше простой, чем два
   хозяина.
5. **R не принимает state без действующего токена.** Приёмник спрашивает W
   (с кэшем ~2 с): если токен не текущий — `409`. Бывший основной, у которого
   сеть «ожила» после раздела, не сможет затереть реплику.

## Что происходит при отказах

| отказ | поведение |
|---|---|
| P упал | аренда истекает через TTL → R забирает и поднимается |
| P завис (жив, но не продлевает) | то же: TTL истёк → R поднимается; P при возврате обнаруживает потерю аренды и останавливает ВМ |
| сеть P↔W, но R↔W жива | P теряет аренду и встаёт, R поднимается — правильный выбор |
| сеть R↔W | R не поднимается; P продолжает работу (его аренда жива) |
| **W недоступен** | P останавливает ВМ после TTL, R не поднимается. **Оба стоят.** Это осознанный выбор в пользу безопасности: без арбитра автоматика невозможна |
| раздел сети пополам | побеждает тот, у кого аренда; второй встаёт |

## Границы (честно)

- **Fencing только на данных**, а не на диске. Старый основной может писать в
  *свой* образ — это его копия, вреда нет. Вред был бы в отправке state, и она
  закрыта токеном.
- **Кворум из одного свидетеля**, а не из большинства: W — единственная точка
  отказа арбитража. Если нужна устойчивость к падению самого W, его надо
  ставить на третью машину с надёжным диском (это конфигурация, а не код).
- **Часы**: W использует только свои часы; от клиентов время не принимается.
  Перезапуск W обнуляет аренды — это безопасно (все встанут и заново
  разыграют), но означает паузу.
- **Никакого TLS** — как и у реплики, сеть считается доверенной (LAN/VPN).

## API (`/witness/v1/`), HTTP, заголовок `X-Hv86-Token`

| метод | запрос | ответ |
|---|---|---|
| `POST /claim` | `?vm=<id>&holder=<имя>` | `{granted, token, ttl_sec}` или `{granted:false, expires_in_sec}` |
| `POST /renew` | `?vm=<id>&token=<t>` | `{ok:true, ttl_sec}` / `409` если не владелец |
| `POST /release` | `?vm=<id>&token=<t>` | `{ok:true}` |
| `GET /status` | `?vm=<id>` | `{holder, expires_in_sec, token_fingerprint}` |

Токен аренды в открытом виде нигде не хранится: W пишет только его SHA-256
(`token_fingerprint`), клиент получает сам токен один раз при `claim`.

## Настройки

- VM (`vm.json` → `ft`): `lease_url`, `lease_token`, `auto_promote`.
- Свидетель: `hv86 --witness <порт> <токен>`; состояние —
  `%HV86_ROOT%\witness\leases.json` (атомарная запись).

## Проверки

- `--unit`: выдача и продление, отказ второму при живой аренде, передача после
  истечения, смена токена, отказ приёмника реплики на чужой/просроченный токен.
- `--itest`: основной держит аренду → перестаёт продлевать → реплика забирает
  и поднимается сама; при этом старый токен уже не принимается.
