# Быстрый старт из пресета: почему не сделали

Идея: пресеты должны стартовать не за секунды холодной загрузки, а из готового
состояния («frozen boot»). Фича была реализована целиком — локальный кэш
состояний на пресет, съём после того, как гость успокоился, одноразовая подстановка
через `--restore` — и **измерена**. Результат отрицательный, код убран.

Здесь остаются замеры, чтобы к идее не возвращались вслепую.

## Замеры

FreeDOS 7.22 (дискета 720K + диск 16 МБ, 32 МБ RAM), старт из консоли:

| | холодный | из кэша |
|---|---|---|
| первые инструкции гостя | **999 мс** | **994 мс** |
| размер состояния | — | 23 МБ |

TinyCore Linux 11 (ISO 20 МБ + диск 256 МБ, 128 МБ RAM):

| | холодный | из кэша |
|---|---|---|
| «запуск эмулятора» → первые инструкции | **6.0 с** | **10.2 с** |
| размер состояния | — | **298 МБ** |

## Почему не работает

1. **Состояние v86 включает диск.** Не только «грязные» блоки: в state попадает
   весь образ, который эмулятор держит в памяти. Отсюда 23 МБ для диска 16 МБ и
   298 МБ для диска 256 МБ. Кэш на 139 пресетов — это десятки гигабайт, а не
   «сотни мегабайт», как казалось на бумаге.
2. **Восстановление большого состояния медленнее загрузки.** 298 МБ уезжают в
   страницу по HTTP-Range и разбираются — 10 с против 6 с холодного старта.
   Кэш не ускоряет, а замедляет.
3. **У маленьких гостей ускорять нечего.** Первые инструкции появляются за ~1 с
   в обоих случаях: это WebView2 + загрузка wasm + инициализация v86, а не гость.
   Даже если бы состояние восстанавливалось мгновенно, выигрыш — доли секунды.

То есть выигрыш есть только там, где кэш дорогой, и его нет там, где кэш дешёвый.

## Что осталось в коде

- Лог `BOOT: первые инструкции гостя через N мс` в vmhost — полезный замер
  времени старта сам по себе, без всякого кэша.
- Поле `preset` в `vm.json`: теперь видно, из какого пресета создана ВМ
  (пригодится и для статистики, и для будущих фич).

## Когда возвращаться к идее

- Если v86 научится сохранять **только изменённые блоки** (или мы перейдём на
  дельты образа), состояние станет дешёвым по размеру.
- Если старт страницы перестанет доминировать (сейчас ~1 с на WebView2 + wasm):
  тогда разница между «BIOS+загрузчик+ядро» и «восстановление» станет заметной.
- Промежуточный вариант, который стоит проверить первым: кэшировать **только
  CD/флоппи-пресеты без жёсткого диска** — там state ≈ RAM (6–8 МБ), а выигрыш
  ограничен временем загрузки гостя (у DOS-комплектов 2–4 с).

Проверять гипотезу просто: `BOOT`-лог даёт время до первых инструкций, дальше
сравниваются два запуска одной ВМ — холодный и из `--restore`.
